01
lens one · TRIZ contradiction

Refusing the trade-off

TRIZ says: when you are asked to choose between two goods, the choice itself is the defect. Three contradictions came up. None were split down the middle; each was dissolved by separating the two goods in time, in direction, or in ownership.

want

Projection push-down needs
dependency annotations.

VS
want

Nobody should annotate deps
just to define a DTO.

resolved — separation in time by coach

Deps are optional at createMap, required only when projectionFor is called. The error names exactly which resolvers need annotating. Projection stops being an entry fee and becomes an opt-in upgrade.

want by user

Cache the mapping result.
Speed.

VS
want

Correctness. The cache goes
stale when the entity changes.

resolved — shrink the lifetime by coach

Staleness is not a function of caching. It is a function of cache LIFETIME. Shrink the lifetime to a single map operation and staleness becomes structurally impossible — no time passes in which the entity could change.

the same shape again by user

Validation rules have the lifetime problem too.

They live on the mapper forever. Same defect, different subsystem — spotted by the developer, unprompted.

decision — CUT by coach

The mapper-lifetime result cache is dead weight.

Deleted. Replaced by the per-operation identity map, which delivers batching and cycle detection out of the same object.

want

Validate mapped values.

VS
want

Don't re-validate everything
read out of your own DB.

resolved — separation in direction by coach

Validation is direction-asymmetric. It belongs on the write path (CreateDto → Entity) only. Entities read from your own database do not need value validation. And don't compete with class-validator — consume it as a SchemaAdapter: its decorators already are schema metadata for the DTO side (nullability, types, enum values).

open question by coach

A gap in DESIGN.md.

Adapters describe entities (TypeORM, Prisma). What produces the descriptor for the DTO side? Strict mode needs one. Candidates on the table: a class-validator adapter, a decorator adapter, or TS-type codegen. Act II answers it with something none of the three.

the observation that unlocked reverse mapping by user

The read path and the write path are not mirrors.

id is DB-generated. So are the timestamps. The write DTO should not send them.

unlock by coach

Reverse mapping is only correctly implementable because of schema adapters.

TypeORM already exposes isGenerated / isPrimary / isCreateDate / isUpdateDate; Prisma's DMMF has @default and @updatedAt. The two rows in that table that break the mirror are exactly the two things a descriptor can see and a decorator cannot. The developer's headline feature is enabled by the adapter decision he had already approved — not in competition with it.

02
lens two · failure analysis

Autopsy on deleted code

Two bodies on the table: four annoyances the developer had actually hit in production, and one function that was shipped and then removed. The lens asks the only question that matters — do these share a cause of death?

specimen A — lived experience by user
  • Setup tax. Four packages, plus the transformer plugin, plus a profile, plus decorating every property — before a single field maps.
  • Contentless errors. "Mapping is not found". No pair, no neighbours, no file, no suggestion.
  • Nested silence. Nested mapping needs @AutoMap(() => T) and a separate createMap. Forget either and you get undefined, silently, at runtime.
  • Selector pain. forMember selector and generic types fight the editor rather than helping it.
specimen B — the deleted function cause of death
reverseMap() — shipped in @nartc/automapper, absent from @automapper/core
mechanism
Relations are not mirror images. The read side expands to a nested DTO; the write side takes a foreign key id. Auto-reversal produces a map that type-checks and is semantically wrong.
aggravator
No schema knowledge to separate DB-owned fields from user-supplied ones — so id and the timestamps get reversed straight back into the write path.
verdict
Not a missing feature. A feature that could not be made correct on the information the library had.
design rule by coach

Errors are a headline feature, not error handling.

Descriptors let us print what automapper structurally cannot: registered neighbours, did-you-mean, the file to fix. And they fire at boot, not per request.

AutomapperError no mapping registered for User → ReadUserDto registered neighbours User → ListUserDto User → AdminUserDto did you mean ReadUserDto declared at src/users/dto/read-user.dto.ts:12 fix here src/users/users.module.ts:8 detected at boot — AutomapperModule.forRoot({ validate: true }) not at request time, with a real user waiting.
consequence of the root cause by coach

Auto-register nested pairs.

The adapter knows User.address is a relation to Address. The DTO descriptor knows ReadUserDto.address is AddressDto. The nested pair is derivable — so register it, or fail at boot naming it. Never silent undefined.

consequence of the root cause by coach

Typed dependency paths.

deps should be a Path<S> union, not string[]. A typo becomes a compile error. This beats automapper's forMember selector ergonomics on its own ground.

keystone by coach

Pick(Entity, [...]) — a real runtime class.

The answer to Act I's open question, and it was none of the three candidates. Like Nest's PickType, it returns an actual class at runtime — so there is runtime metadata without a single decorator. It inherits nullability and column names from the entity descriptor, and it makes a DTO fail to compile when a column is renamed.

src/users/dto/read-user.dto.tsno decorators · no profile · no createMap
export const ReadUserDto = Pick(User, ['id', 'firstName', 'lastName', 'address']);

// column renamed in the entity? this line stops compiling. that is the feature.
crack found in the design by user
Declaring fullName in the DTO and again in the config is repetitive — two places for one field.

The third instance of the developer's own recurring question. Not "is this slow" or "is this typed", but where does this thing actually belong?

answer by coach

extend() — the resolver is the declaration.

One object gives TypeScript the field type (inferred from the compute return type) and gives the runtime both the field list and the resolver. export const + export type declaration merging keeps it usable as a class.

one declaration site, not twotype inferred from the resolver
export const ReadUserDto = Pick(User, ['id', 'address'])
  .extend({
    fullName: (u) => `${u.firstName} ${u.lastName}`,  // : string, inferred
    email:    visible(ctx => ctx.isAdmin, u => u.email), // : string | undefined
  });

export type ReadUserDto = InstanceType<typeof ReadUserDto>;
cost of extend() by coach

A field with no syntactic declaration site cannot carry @ApiProperty.

Which breaks Swagger for Nest users — the exact audience. It also blocks one DTO mapped from two different sources.

answer to the cost by coach

Generate the OpenAPI schema from the descriptor.

schemaOf(ReadUserDto). We already know types, nullability and enums. The cost turns into another differentiator.

runtime check → type error by coach

visible() widens to T | undefined.

So the inferred DTO type is honest. This replaces DESIGN.md open question 2 outright: "strict rejects visible() on required fields" stops being a runtime rule and becomes a type error.

runtime throw → editor squiggle by coach

resolve() brands the DTO async.

It unwraps to Awaited<R> and marks the DTO. Calling mapper.map() on an async DTO becomes a compile error — upgrading decision 5 from a runtime throw to a red underline.

logged here, belongs to the next lens by coach

Radical flip: if the DTO determines the SELECT, never hydrate an entity at all.

mapper.query(User, ReadUserDto, { where }) compiles the DTO shape straight to SQL; rows map in a single pass. The mapper stops being an object transformer and becomes a DTO-to-query compiler.

It arrived before the technique switch — the session ran ahead of its own agenda. Remember it: it comes back at the end as the strongest idea nobody is allowed to build yet.

03
lens three · assumption reversal

Turning the foundations over

Every mapping library since AutoMapper for .NET has assumed you register a pair. The lens asks what survives if you simply don't.

assumption 1

You must call createMap(source, destination) to register a pair.

reversed by coach

Never call createMap. Pick(User, ...) already names the source — so the DTO is the registration. Profiles survive only for multi-source DTOs.

the objection this raises

Lazy registration pushes strict errors to first call — you lose boot-time safety.

absorbed by coach

A boot-time sweep. AutomapperModule.forRoot({ validate: true }) builds every plan on onModuleInit and fails the boot; npx automapper check does the same in CI. Boot-time strictness with zero createMap.

Composed with everything before it, the read path collapses to a DTO definition and a one-line controller. Here is the whole diff against the incumbent.

@automapper/core — today7 steps before one field maps
// 1 · four packages
npm i @automapper/core @automapper/classes
       @automapper/nestjs @automapper/types

// 2 · transformer plugin — nest-cli.json
"plugins": ["@automapper/classes/transformer-plugin"]

// 3 · decorate every property, on both sides
class User {
  @AutoMap() id: string;
  @AutoMap() firstName: string;
  @AutoMap() lastName: string;
}

// 4 · nested needs the type thunk — or silent undefined
@AutoMap(() => Address) address: Address;

// 5 · a profile class
@Injectable()
export class UserProfile extends AutomapperProfile { … }

// 6 · createMap per pair — and again for every nested pair
createMap(mapper, User, ReadUserDto);
createMap(mapper, Address, AddressDto); // forget = undefined

// 7 · forMember for anything computed
forMember(d => d.fullName,
  mapFrom(s => `${s.firstName} ${s.lastName}`))
// ↑ fullName also declared on the DTO. two places, one field.
@nestjs-automapper — proposed4 steps, one of them is the controller
// 1 · the DTO is a Pick of the entity — and IS the registration
export const ReadUserDto = Pick(User, ['id', 'address'])

// 2 · computed fields: the resolver IS the declaration
  .extend({
    fullName: (u) => `${u.firstName} ${u.lastName}`,
  });
export type ReadUserDto = InstanceType<typeof ReadUserDto>;

// 3 · one module option — boot fails if any plan is unbuildable
AutomapperModule.forRoot({ validate: true });
//   $ npx automapper check   ← same sweep, in CI

// 4 · the controller
@Get()
list() {
  return this.users.projectionFor(ReadUserDto).find();
}

// no decorators.        no transformer plugin.
// no profile.           no @AutoMap(() => T).
// no createMap.         nested pair auto-registered.
// address relation resolved from the schema, not from you.
composite hello-world by coach

Pick + extend + no-createMap + query() reduces the entire read path to a DTO definition plus a one-line controller: no decorators, no profile, no createMap, no transformer plugin, no repo.find, no entity hydration.

won't · this time

mapper.query(User, Dto, { where }) — the DTO-to-query compiler

Judged the strongest idea of the session. Deliberately not built.

the idea that won and was shelved anywayrevisit as 3.0
// no repo.find. no entity hydration. the DTO shape IS the SELECT.
const rows = await mapper.query(User, ReadUserDto, { where: { active: true } });
//    ↑ compiles straight to SQL, rows map in one pass
why it won

It is the logical end of the schema-ground-truth thesis. If the library truly knows your schema, hydrating an entity just to throw most of it away is waste.

why it's shelved

It turns a mapper into a query builder — dialects, joins, pagination. That is a different product with a different maintenance surface.

what covers it meanwhile

Projection push-down (MUST #5) proves the same claim far more cheaply. The demo lands; the query engine doesn't have to be written.

05
synthesis · the through-line

One capability, not sixteen features

Not a mapper with more features.
The mapper that knows your schema.

Every annoyance the developer hit — the setup tax, the contentless errors, the silent nested undefined, the selector type pain — and the deletion of reverseMap trace to the same absence. Which means the sixteen items on that ladder are not a wish list. They are consequences. Ship the capability and they follow; ship them individually and you have built a competitor's changelog.

synergy the developer found without naming it by coach

Precondition and payoff, mistaken for two ideas.

His headline ask — reverse mapping — is only correctly implementable because of the schema-adapter decision he had already approved. He thought he had two features. He had one feature and its enabling condition.

synergy from his own contradiction by coach

One object, three unrelated problems.

His caching-vs-correctness contradiction produced the per-operation identity map, which independently solves cycle detection, nested-object dedupe, and async resolver batching.

the pattern behind his three sharpest moves by coach

Cache staleness. Validation lifetime. The fullName repetition. Three different subsystems, one question:

“what is the correct LIFETIME
or DECLARATION SITE for this thing?”

That question, not any single idea, is the session's real method — and it should be pointed at every future feature before it ships.
