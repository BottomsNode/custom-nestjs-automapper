- (insight by coach) VERIFIED: @automapper/core has no reverseMap. Legacy @nartc/automapper HAD reverseMap(); the rewrite dropped it. Removal implies it was hard to do correctly, not merely forgotten.
- (note by coach) @automapper/core surface: config = afterMap/afterMapArray/autoMap/beforeMap/beforeMapArray/constructUsing/extend/forMember/forSelf/namingConventions/typeConverters; members = condition/convertUsing/fromValue/ignore/mapDefer/mapFrom/mapInitialize/mapWithArguments/mapWith/nullSubstitution/preCondition/undefinedSubstitution. compile-mapping.ts exists, so it does precompile.
- (direction by user) Goal is parity with automapper at lower code cost, PLUS features it lacks. User invites having weak ideas cut.
- (decision by user) Batch chosen (facilitator-chosen): TRIZ Contradiction, Failure Analysis, Assumption Reversal, Kill the Crown Jewel
- (technique) started TRIZ Contradiction
- (idea by coach) Resolve deps-vs-verbosity by separation in time: deps optional at createMap, required only when projectionFor is called. Error names exactly which resolvers need annotating. Projection becomes opt-in upgrade, not entry fee.
- (idea by user) Core contradiction: caching vs correctness - cache goes stale when the entity changes
- (insight by coach) Staleness is a function of cache LIFETIME. Shrink lifetime to one map operation and staleness becomes structurally impossible - no time passes for the entity to change.
- (idea by user) Validation rules have the same lifetime problem - they live on the mapper forever
- (decision by coach) CUT: mapper-lifetime result cache is dead weight. Replace with per-operation identity map (also delivers resolver batching + cycle detection from the same object).
- (insight by coach) Validation is direction-asymmetric: it belongs on the WRITE path (CreateDto -> Entity). Entities read from your own DB do not need value validation.
- (idea by coach) Do not compete with class-validator - CONSUME it as a SchemaAdapter. class-validator decorators ARE schema metadata: gives nullability, types, and enum values for the DTO side.
- (question by coach) GAP in DESIGN.md: adapters describe ENTITIES (TypeORM/Prisma). What produces the descriptor for the DTO side? Strict mode needs it. Candidates: class-validator adapter, decorator adapter, TS-type codegen.
- (idea by user) Read/write asymmetry: id is DB-generated, timestamps too - the write DTO should not send them
- (insight by coach) WHY reverseMap was deleted from automapper: relations are not mirror images (read expands to nested DTO, write takes a foreign key id), and it had no schema knowledge to tell DB-owned fields from user-supplied ones. Auto-reverse produces valid-looking, semantically wrong maps.
- (idea by coach) UNLOCK: reverse mapping is only correctly implementable BECAUSE of schema adapters. TypeORM (isGenerated/isPrimary/isCreateDate/isUpdateDate) and Prisma DMMF (@default, @updatedAt) already mark DB-owned fields. User headline feature is enabled by the adapter decision, not competing with it.
- (technique) started Failure Analysis
- (idea by user) Real automapper annoyances hit: (1) setup tax - 4 packages + transformer plugin + profile + decorate every property before anything maps; (2) 'Mapping is not found' error with no context; (4) nested mapping needs @AutoMap(()=>T) AND a separate createMap or silent undefined; (6) forMember selector/generic type pain
- (insight by coach) ROOT CAUSE unifying all four annoyances AND the reverseMap deletion: automapper has no schema ground truth. It cannot auto-register nested pairs, cannot suggest the missing map, cannot verify anything - so it demands the user restate what the types already say, then fails silently when they forget.
- (decision by coach) Design rule: errors are a headline feature. Descriptors let us print what automapper structurally cannot - registered neighbours, did-you-mean, the file to fix. And they fire at boot, not per request.
- (idea by coach) Auto-register nested pairs: adapter knows User.address is a relation to Address; DTO descriptor knows ReadUserDto.address is AddressDto. The nested pair is derivable - register it or error at boot naming it. Never silent undefined.
- (idea by coach) Typed dep paths: compute deps should be a Path<S> union, not string[], so a typo is a compile error. Beats automapper's forMember selector ergonomics.
- (idea by coach) KEYSTONE: Pick(Entity, [...]) helper returns a real runtime class (like Nest PickType). Solves the no-runtime-metadata problem without decorators, inherits nullability + column names, and makes DTOs fail to COMPILE when a column is renamed.
- (crack by user) Declaring fullName in the DTO AND again in the config is repetitive - two places for one field
- (idea by coach) Fix the repetition with extend(): the resolver IS the declaration. TS infers the field type from the compute return type; runtime gets field list and resolver from one object. export const X + export type X declaration merging keeps it usable as a class.
- (crack by coach) COST of extend(): a field with no syntactic declaration site cannot carry @ApiProperty, breaking Swagger for Nest users. Also blocks one DTO mapped from two different sources.
- (idea by coach) Answer to the Swagger cost: generate the OpenAPI schema FROM our descriptor - schemaOf(ReadUserDto). We know types, nullability, enums already. Turns a cost into another differentiator.
- (idea by coach) visible() must widen its return to T|undefined so the inferred DTO type is honest. This replaces DESIGN.md open question 2: 'strict rejects visible() on required fields' becomes a TYPE error, not a runtime check.
- (idea by coach) resolve() unwraps to Awaited<R> and brands the DTO async, so mapper.map() on an async DTO is a COMPILE error. Upgrades decision 5 from runtime throw to editor squiggle.
- (idea by coach) RADICAL FLIP (assumptions 4+5): if the DTO determines the SELECT, never hydrate an entity. mapper.query(User, ReadUserDto, {where}) compiles DTO shape straight to SQL, rows map in one pass. Mapper stops being an object transformer and becomes a DTO-to-query compiler.
- (technique) started Assumption Reversal
- (idea by coach) FLIP assumption 1: never call createMap. Pick(User,...) already names the source, so the DTO IS the registration. Profiles survive only for multi-source DTOs.
- (idea by coach) Lazy registration would push strict errors to first call. Fix: boot-time sweep - AutomapperModule.forRoot({validate:true}) builds every plan onModuleInit and fails the boot, plus 'npx automapper check' for CI. Keeps boot-time strictness with zero createMap.
- (insight by coach) Composite hello-world: Pick + extend + no-createMap + query() reduces the entire read path to a DTO definition plus a one-line controller. No decorators, no profile, no createMap, no transformer plugin, no repo.find, no entity hydration.
- (technique) started convergence: MoSCoW
- (decision by user) MoSCoW APPROVED AS-IS. MUST for 2.0: (1) Pick(Entity,[...]) runtime-real DTO class; (2) extend() so the resolver is the declaration; (3) error quality - did-you-mean + registered neighbours + file pointer; (4) boot-time validation sweep validate:true plus 'npx automapper check'; (5) projection push-down projectionFor/@Projection; (6) typed dep paths Path<S> not string[]; (7) auto-register nested pairs; (8) per-operation identity map; (9) reverse map for SCALAR fields only, dropping id/timestamps/generated.
- (decision by user) SHOULD (2.0 if time): (10) no createMap - DTO is the registration; (11) context-gated fields visible() with T|undefined type widening; (12) class-validator as a SchemaAdapter for non-Pick DTOs; (13) reverse map for relations to foreign keys - the half that killed automapper's version.
- (decision by user) COULD (2.1+): resolve() async branding as compile error; deps optional until projectionFor is called; schemaOf(Dto) OpenAPI generation.
- (decision by user) WON'T THIS TIME: mapper.query(User,Dto,{where}) - the DTO-to-query compiler. Judged the strongest idea of the session but it turns a mapper into a query builder (dialects, joins, pagination). Projection push-down proves the same claim far cheaper. Revisit as 3.0.
- (insight by coach) THE THROUGH-LINE: every annoyance the user hit with automapper (setup tax, contentless errors, silent nested undefined, selector type pain) AND the deletion of reverseMap trace to one root cause - automapper has no schema ground truth. So the product is not 'a mapper with more features', it is 'the mapper that knows your schema'. Every MUST item is a consequence of that single capability, which makes the roadmap coherent rather than a feature list.
- (insight by coach) SYNERGY the user found without naming it: their headline ask (reverse mapping) is only correctly implementable BECAUSE of the schema-adapter decision they had already approved. The two ideas they thought were separate are precondition and payoff.
- (insight by coach) SYNERGY: the user's own caching-vs-correctness contradiction produced the per-operation identity map, which independently solves three unrelated problems - cycle detection, nested-object dedupe, and async resolver batching. One object, three features.
- (insight by coach) PATTERN: the user's three sharpest contributions (cache staleness, validation lifetime, fullName repetition) were all instances of one meta-question - 'what is the correct LIFETIME or DECLARATION SITE for this thing?'. That question is the session's real method and should be reused on every future feature.
- (decision by user) AMENDMENT after MoSCoW approval: schemaOf(Dto) OpenAPI generation PROMOTED from COULD to MUST. Reason: extend() is MUST and strips the syntactic declaration site that @ApiProperty needs, so shipping extend() without schemaOf() would ship a Swagger regression in 2.0. Resolves the open question 'Swagger cost of extend()'.
