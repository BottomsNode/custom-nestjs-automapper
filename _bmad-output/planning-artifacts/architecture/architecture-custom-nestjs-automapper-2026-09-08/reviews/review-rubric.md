- **Target:** `_bmad-output/planning-artifacts/architecture/architecture-custom-nestjs-automapper-2026-09-08/ARCHITECTURE-SPINE.md`

## Findings

### CRITICAL

**F1 — CRITICAL — AD-1 makes CAP-9 and CAP-8 unimplementable as written; the IR is never stated to carry the type metadata those back-ends need.**
AD-1's Rule: *"Back-ends consume `MappingPlan` only and must not import an adapter or a descriptor type."* But `core/schema` is a back-end, and CAP-9 requires it to emit "correct type, nullability, enum values, arrays, and nested DTO references" — all of which live in `FieldMeta` (`type`, `nullable`, `enumValues`) per `api-surface.md`. Same for CAP-8: `reverse()` needs `isPrimary`/`isGenerated`/`isCreateDate`/`isUpdateDate`/`isDeleteDate`. Nothing in the spine says `MappingPlan`/`ResolutionNode` carries descriptor-derived type or provenance metadata; AD-10 mentions only `deps`. So an implementer has two mutually exclusive readings — embed `FieldMeta` into plan nodes, or let the schema/reverse back-ends read descriptors — and the spine picks neither. **Why it matters:** this is the highest-traffic ambiguity in the document. The two readings produce incompatible `MappingPlan` shapes, and `MappingPlan` is the single artifact every back-end shares. Getting it wrong late means re-cutting the IR. **Fix:** add to AD-2 (or a new AD) that *every* `ResolutionNode` carries a resolved, descriptor-independent `TypeShape` (type tag, nullability, enum values, array-ness, nested plan reference) plus provenance flags, materialised at plan build; and state explicitly that back-ends may never re-derive type information. Then AD-1's ban becomes satisfiable rather than contradictory.

**F2 — CRITICAL — The DTO construction contract — the mechanism the whole thesis rests on — is governed by zero ADs.**
`Pick(Entity, [...]) + extend(..., { compute(...) })` returning a real runtime class with real own-properties, declaration-merged as value and type, is what delivers CAP-1, CAP-2, CAP-9 and CAP-10. The spec's Resolved section calls it out as spike-proven and the api-surface flags the exact v1-regression trap ("the helper's constructor must assign each key, even as `undefined`"). The spine mentions it only as a Structural Seed directory (`core/dto/ # Pick, extend, resolvers, Path<S>`). No invariant states: a DTO class exposes a runtime field registry equal to picked-plus-computed keys; every field has exactly one declaration site (a spec Constraint, line 81); instances carry own-properties for every registered key. **Why it matters:** the single defect that killed v1 was a presence check that was always false because instances had no own-properties. The spine names AD-4 for v1's *other* defect (`class.name` keys) but leaves v1's *primary* defect ungoverned. **Fix:** add an AD — "A DTO's runtime descriptor is authoritative and complete" — requiring: (a) every registered key exists as an own-property on every instance, initialised to `undefined` if unresolved; (b) the runtime key set is exactly picked ∪ computed, asserted by a test; (c) no field may be declared in more than one place; (d) any presence test in codegen uses the runtime registry, never `in`/`hasOwnProperty` against a bare instance.

**F3 — CRITICAL — The packaging and consumer-toolchain dimension is entirely silent.**
Not decided, not deferred, not an open question. Missing outright: module format (CJS / ESM / dual), `package.json` `exports`/`types`/`type` fields, `engines` / supported Node range, the consumer's required tsconfig (`strict`, decorator model, `useDefineForClassFields`, `moduleResolution`), and the minimum consumer TypeScript version. **Why it matters, concretely:** (i) NestJS apps are CJS by default while the spine's toolchain is TS 6/7 — a dual-publish decision made independently in three packages is a guaranteed divergence on day one; (ii) the `nestjs` package ships `@MapTo` / `@Projection` decorators, and legacy `experimentalDecorators` vs TC39 standard decorators cannot be mixed in a consumer file — NestJS and TypeORM both require the legacy model, so this must be *stated*, not assumed; (iii) `useDefineForClassFields` directly changes whether class fields become own-properties, which is exactly the mechanism F2 depends on; (iv) `AsyncLocalStorage` and `new Function` constrain the Node floor. **Fix:** add a "Runtime & packaging envelope" AD fixing: module format and `exports` map shape (identical across all three packages), `engines.node` range, the decorator model required of consumers, `useDefineForClassFields: false` (or an explicit statement that the `Pick` helper does not depend on it), and the minimum consumer TypeScript version with a CI job that compiles the reference hello-world at that floor.

### HIGH

**F4 — HIGH — AD-4 (constructor-identity keys, `Map`/`WeakMap`) makes CAP-4's headline error message impossible.**
CAP-4's success criterion, echoed verbatim in the api-surface error sample, is `Maps registered from User: AdminUserDto, UserSummaryDto` — i.e. enumerate all destinations registered for a source. A `WeakMap` is not enumerable. AD-4 offers `Map`/`WeakMap` as interchangeable and the Consistency table says the pair key is "the tuple `(sourceCtor, destCtor)`, never a string" — but a tuple is not usable as a `Map` key by identity, so the actual structure (nested `Map<Ctor, Map<Ctor, Entry>>`? `WeakMap<Ctor, Map<...>>`?) is undecided. **Why it matters:** two implementers will pick different structures, and one of them silently cannot satisfy CAP-4. **Fix:** AD-4 should mandate the exact structure — an enumerable outer `Map` keyed on `sourceCtor` holding an inner `Map` keyed on `destCtor` — and state that the registry must support "list destinations for source" as a first-class read, since CAP-4 depends on it.

**F5 — HIGH — Two different things are called "context", and AD-7 governs only one of them.**
AD-7: *"Per-map state … lives on a context created per top-level `map` call and discarded when it returns. No module-level mutable state anywhere."* The api-surface has a *second*, unrelated context: user `Ctx` from `contextFactory: req => ({...})`, reaching the mapper through `AsyncLocalStorage` in the `nestjs` package, request-scoped — it does **not** begin and end with a `map` call. AD-7 does not mention it, does not permit it, and the naming collision means an implementer reading only the spine will conflate the two. `AsyncLocalStorage` appears nowhere in the ADs despite being in the Structural Seed. **Why it matters:** this is precisely a cross-package divergence — `core` threads `ctx` explicitly, `nestjs` threads it ambiently, and the lifetime boundary between them is where cross-request leakage (the thing AD-7 exists to prevent) actually happens. **Fix:** rename one of the two (`OperationContext` vs `UserContext`/`Ctx`), and extend AD-7 to state the ALS store's lifetime, who creates it, and that `core` never reads ambient state — the user context enters `core` only as an explicit parameter.

**F6 — HIGH — Context-gated fields are absent from the spine entirely, though the spec makes them a hard constraint.**
SPEC Constraint: *"Projection throws when the plan contains context-gated fields and no context is supplied. Projecting the union of all contexts is excluded."* The api-surface has `visible(pred, inner?)`, `projectionFor(s, d, { ctx })`, and the note that "an admin request projects more columns than a public one". The spine has zero occurrences of gating, `visible`, or context-dependent projection: no `ResolutionNode` kind, no AD, no row in the Capability map, no mention in AD-10. **Why it matters:** AD-10 says the projector "unions their declared `deps`" — read literally, that is the *union across all contexts* behaviour the spec explicitly forbids as the failure CAP-5 exists to prevent. The spine's only projection invariant contradicts the spec's projection constraint. **Fix:** add a `gated` node kind to AD-2's closed union, and amend AD-10: gated nodes contribute deps only when their predicate is evaluable against a supplied context; `projectionFor` throws (`AutomapperError` with a code) when a plan contains gated nodes and no context is supplied.

**F7 — HIGH — Cycle policy has no invariant; CAP-7's row cites AD-7, which says nothing about it.**
SPEC Constraint (line 79) is dense and load-bearing: ancestor chain not a global visited set; a repeated reference reachable by two paths is shared data and must still map; a true back-edge on a non-optional field fails at boot; on an optional field the default is omission with a per-map reference-marker mode; a depth ceiling backstops the runtime. The spine reduces all of that to five words inside AD-7's parenthetical list ("identity map, ancestor chain, resolver memo"). **Why it matters:** three units must agree here — the boot-time plan validator (back-edge detection), the runtime context (ancestor chain), and codegen (depth ceiling, omission vs marker). "Ancestor chain" as a bare noun in a list does not stop an implementer from writing a global visited set, which would break CAP-7's shared-object requirement (5 invocations, not 100) in a way no test named in the spine would catch. **Fix:** promote the constraint to its own AD with the four rules stated, and cite it in CAP-7's map row alongside AD-7.

**F8 — HIGH — The reverse-mapping provenance rule has no AD, and CAP-8's cited ADs do not govern it.**
SPEC Constraint: *"Reverse mapping determines database-owned versus user-supplied fields from schema descriptors only. Naming heuristics are excluded."* CAP-8's map row cites AD-1 and AD-2 — direction and node-set closure — neither of which forbids `if (name.endsWith('At'))`. **Why it matters:** the naming-heuristic shortcut is the obvious, tempting implementation, and it is exactly the failure mode the spec calls out. Also unresolved: is `reverse()` a planner operation or a back-end? If a back-end, AD-1 forbids it the provenance flags it needs (see F1). **Fix:** add an AD binding CAP-8 — "provenance comes from `FieldMeta` flags only; no rule may read a field's name" — and state where `reverse()` sits in the pipeline.

**F9 — HIGH — The adapter port's type vocabulary is not closed, while the IR's is — the same divergence class, treated asymmetrically.**
AD-2 rightly closes `ResolutionNode.kind` with a `never` exhaustiveness check. The other port — `FieldMeta.type` (`'string' | 'number' | 'boolean' | 'date' | 'json' | 'enum' | 'unknown'`) — has no equivalent invariant. CAP-9's schema emitter must switch exhaustively over it, and 2.1 adds a second adapter (Prisma) with a different native type space. **Why it matters:** an adapter that widens `FieldMeta.type` breaks the schema back-end silently, which is the identical failure AD-2 was written to prevent one layer up. **Fix:** extend AD-2 (or add AD-2b) to close `FieldMeta.type` and `RelationMeta.kind` under the same rules — closed union, exhaustive switch, `never` check, adding a member is a breaking change to `core`.

**F10 — HIGH — AD-8 is not enforceable and prevents nothing.**
Rule: *"A rule must be enforced at the leftmost **feasible** rung."* "Feasible" is a judgment word; two engineers disagreeing about feasibility both comply. There is no mechanism, no check, and no list of which rules sit at which rung. Its stated Prevents — *"divergent choices about where a given rule is enforced"* — is exactly what a judgment-word rule cannot stop. **Why it matters:** CAP-3 ("fails at boot") and CAP-10 ("fails `tsc`") are both mapped to AD-8, so the two capabilities whose success criteria are *about* enforcement location rest on the one AD that does not fix an enforcement location. **Fix:** replace the ladder metaphor with a concrete table — one row per rule (unresolved destination field, unknown dep path, nested pair underivable, non-optional back-edge, sync call on async plan, projection without context, unregistered pair), one column for its rung — and require `validateAll()` to run exactly the boot-rung set.

**F11 — HIGH — AD-11's enforcement mechanism is deferred out of existence, and its gate does not cover the evidence CAP-1/2/10 depend on.**
AD-11 says *"CI must additionally type-check the published `.d.ts` under TypeScript 7.x."* No CI system is named anywhere in the spine, and Deferred item 1 postpones the release pipeline. Worse, type-checking the `.d.ts` is the *weak* gate: CAP-1, CAP-2 and CAP-10 are all about the consumer's compiler *rejecting* bad code, and the only evidence for that is the spike's six negative cases — proven under **TypeScript 5.9 / Node 22** per the spec's Resolved section, while the spine mandates emit under TS 6.0.3 and consumers on TS 7.0.2. Declaration merging, the `Pick` value/type namespace trick, and `Path<S>` inference are all exactly the sort of thing that shifts across two majors. **Fix:** name the CI system; make the gate "the spike's positive and negative suites compile (and fail to compile, respectively) under every supported consumer TypeScript major, TS 6 and TS 7 included" — not just a `.d.ts` smoke check.

**F12 — HIGH — `npx automapper check` has no home package, and CAP-3 is half-unimplementable without it.**
CAP-3's success criterion has two halves: startup fails, *and* "the same condition is detectable in CI without starting the application". The api-surface answers the second half with a CLI (`npx automapper check`). The spine ships exactly three packages, its Structural Seed has no `bin/`, and no AD or Deferred item mentions a CLI. Undecided: which package owns the bin, how it loads the user's entities and DTOs without a Nest bootstrap, and its exit-code contract. **Why it matters:** a CLI that must load user TypeScript is a packaging decision entangled with F3 (module format). **Fix:** decide the owning package (likely `core`, keeping it dependency-free, or a documented `nestjs` bin) and state the load mechanism and exit-code contract, or move it to an explicit open question — it cannot stay unmentioned when a capability's success criterion names it.

**F13 — HIGH — Deferred "Cross-package release orchestration" hides three genuine cross-unit interfaces, and AD-2 already contradicts the deferral.**
The deferral's rationale — *"does not affect any interface"* — is false. It conceals: (a) how `typeorm` and `nestjs` depend on `core` (peer? dependency? exact-pin? caret range?); (b) whether the three packages version in lockstep; (c) peer-dependency *ranges* — the Stack table lists `typeorm 1.1.1` and `@nestjs/* 12.0.1` as bare versions, and a library that pins peers exactly is unusable, while one that ranges them too wide breaks. Meanwhile AD-2 already asserts a versioning policy — *"Adding a kind is a breaking change to `core` and must update every back-end in the same commit"* — which is a release-orchestration decision made in an invariant while the section that owns it says the decision can wait. **Fix:** un-defer the *policy* (lockstep majors, `core` as a peer or a pinned internal dep, peer range shape, and whether `@nestjs/swagger` is an optional peer); defer only the *tooling choice* (Nx release config vs changesets).

**F14 — HIGH — Deferred "Adapter capability negotiation" is already interface-visible.**
`SchemaAdapter.toNativeProjection?()` is **optional** in the api-surface, and `Mapper.nativeProjectionFor()` is a public method. What happens when an adapter has no `toNativeProjection`, or has one that cannot express a given `FieldSelection` (e.g. a nested gated relation), is a today-question with a today-visible answer surface — not a 2.1 question. The deferral's rationale ("not decidable from one adapter") justifies deferring the *general negotiation protocol*, not the *failure mode*. **Fix:** decide now that an adapter lacking or unable to satisfy `toNativeProjection` throws a specific `AutomapperError` code carrying the offending selection path; defer only the richer capability-declaration protocol.

### MEDIUM

**F15 — MEDIUM — Back-end count and placement contradict each other.**
The Design Paradigm table lists five back-ends ("Codegen, projector, explainer, plan validator, schema emitter"); the Structural Seed says "The four `core` back-ends are siblings by design"; and the plan validator is placed inside `plan/` — the lowering stage — not as a sibling back-end. **Why it matters:** AD-2's exhaustiveness obligation applies to "every back-end". If the plan validator is not a back-end, is it exempt? If it lives in `plan/`, may it read descriptors (which AD-1 forbids back-ends)? The plan validator is the component behind CAP-3, so its layer assignment is not cosmetic. **Fix:** pick one count, state whether the plan validator is a back-end, and if it is, move it to its own sibling directory.

**F16 — MEDIUM — AD-5 and AD-1 collide over where the error taxonomy lives.**
AD-5 requires adapters to throw `AutomapperError` subclasses; the Structural Seed puts the `AutomapperError` taxonomy inside `core/diagnose/` — a back-end directory. An adapter (a front-end) importing from a back-end inverts AD-1's one-way dataflow at the module level, and would trip any lint rule written to enforce AD-1 literally. **Fix:** move the error taxonomy to a layer-neutral location (`core/errors/`) that both front-ends and back-ends may import, and say so in AD-5.

**F17 — MEDIUM — The `Binds:` fields and the Capability→Architecture Map disagree.**
Every AD cited in the map exists (AD-1, 2, 4, 5, 8, 9, 10, 11) — good. But: AD-3 declares `Binds: codegen, CAP-1, CAP-5` and appears in **neither** the CAP-1 nor the CAP-5 row. AD-6 declares `Binds: all packages` and appears in **no** row. AD-1 and AD-4 declare `Binds: all` yet appear in 4 and 3 rows respectively. AD-8 declares `Binds: CAP-3, CAP-4, CAP-10` but CAP-4's row omits it. **Why it matters:** the map is the lookup table an implementer uses to know which rules apply to the file they are writing; a codegen author reading CAP-1's row will never learn AD-3 governs them. **Fix:** generate the map from the `Binds:` fields, or reconcile them by hand and state which is authoritative.

**F18 — MEDIUM — CAP-2's only governing AD does not govern CAP-2.**
CAP-2 is "a derived field is declared once — one declaration supplies both static type and runtime resolution". Its row cites only AD-9, which is about sync/async plan uniformity. AD-9 has nothing to say about single-declaration-site. Combined with F2, CAP-2 is effectively ungoverned. **Fix:** cite the new DTO-contract AD from F2 in CAP-2's row (and CAP-1's, CAP-9's, CAP-10's).

**F19 — MEDIUM — CAP-6's row omits AD-8 though its success criterion is a boot failure.**
CAP-6: "If the nested pair cannot be derived, startup fails naming that pair — it never yields `undefined`." That is an AD-8 (enforcement rung) and AD-5 (error content) obligation; the row cites only AD-2 and AD-4. Inconsistent with CAP-3's row, which does cite AD-8 for the same class of requirement. **Fix:** add AD-8 and AD-5 to CAP-6.

**F20 — MEDIUM — AD-1 is not mechanically enforceable inside `core`, where most of its violations would occur.**
AD-6 names its enforcement ("lint rule and pnpm's strict resolution"). AD-1's most likely violation — `emit/` or `schema/` importing from `descriptor/` — is *intra*-package, so pnpm cannot see it and no enforcement mechanism is named. **Fix:** name the mechanism explicitly (Nx module-boundary tags per `core` subdirectory, or `eslint no-restricted-imports` banning `descriptor/*` from `emit|project|diagnose|schema`), and add it to the "every mechanically checkable AD gets a test" list.

**F21 — MEDIUM — Stack is verified-current but names no runtime.**
I re-verified all seven entries live against the npm registry on 2026-09-08: `typescript` latest `7.0.2` with `6.0.3` the newest 6.x; `nx 23.2.0`; `pnpm 12.3.4`; `vitest 5.0.0`; `@nestjs/common`, `@nestjs/core`, `@nestjs/swagger`, `@nestjs/testing` all `12.0.1`; `typeorm 1.1.1`; `reflect-metadata 0.2.2`. The `tsup` rejection is also accurate — `8.5.1`, `time.modified 2025-11-12`, ~10 months stale. **The gap:** no Node version appears anywhere in the Stack table, though the spec's spike ran on Node 22 and the design depends on `new Function` and `AsyncLocalStorage`. **Fix:** add a Node row and an `engines` decision (see F3).

**F22 — MEDIUM — A spec Constraint that two implementers could genuinely diverge on is demoted to a conventions table row.**
"Source paths: Dotted strings typed as `Path<S>`" sits in the Consistency Conventions table. The spec states the *reason* as a hard exclusion: *"Proxy tracing and `fn.toString()` parsing are excluded: both under-collect across branches and break under minification, reintroducing silent under-fetch."* That exclusion — the mechanism behind CAP-10 and half of CAP-5 — appears nowhere in the spine. **Why it matters:** proxy tracing is the ergonomic-looking shortcut somebody will propose in month three; a conventions row will not stop it, and the failure it causes (silent under-fetch) is invisible in tests. **Fix:** promote to an AD with the exclusion stated and the reason attached.

**F23 — MEDIUM — An invariant is buried inside the Structural Seed.**
*"The four `core` back-ends are siblings by design: each depends on `plan/`, none on each other, none on `descriptor/`."* That is a rule, not a starting shape, and the Structural Seed is by definition the part code owns and may refactor. **Fix:** move the sentence into AD-1 as an explicit clause; leave only the directory tree in the seed.

**F24 — MEDIUM — Adapter selection is undecided though the API supports multiple adapters.**
`AutomapperModule.forRoot({ adapters: [...] })` takes an array and `SchemaAdapter.supports(type)` is a predicate. Undecided: resolution order, what happens when two adapters both claim a type, and what happens when none does. `TypeDescriptor.producedBy` feeds CAP-4's error text, so the answer is user-visible. **Fix:** state first-match-wins in declaration order, and require a specific `AutomapperError` code when no adapter claims a type, naming the adapters that were consulted.

**F25 — MEDIUM — AD-3's Rule is narrower than its "Prevents" claim.**
The rule covers property-access keys, identifiers, and resolver closures. It does not cover other user-derived values that plausibly reach generated source: `constant(value)` literals, default values, enum members, or path segments rendered into inline comments. The Prevents claim is "code injection", full stop. **Fix:** restate the rule as a total ban — "no user- or metadata-derived value is ever concatenated into generated source; keys use `JSON.stringify` bracket notation and all other values arrive as closure bindings" — which is both broader and easier to check.

**F26 — MEDIUM — AD-9 does not say nested asyncness propagates.**
`isAsync` is "the disjunction over plan nodes". With CAP-6's auto-derived nested pairs, a child plan's asyncness must lift into the parent, and a child registered *after* the parent's plan was built would retroactively change the parent's `isAsync` — colliding with AD-9's "immutable thereafter". **Fix:** state that plan build is bottom-up over the reachable pair graph and that `isAsync` includes the transitive closure over nested plans; state what happens if a nested pair is registered later.

**F27 — MEDIUM — AD-10 depends on a node property AD-2 does not require.**
AD-10 unions "their declared `deps`", but AD-2 — which defines the node set — never says every kind carries a `deps` member. A node kind added without `deps` compiles fine and silently under-fetches. **Fix:** add to AD-2: every `ResolutionNode` variant declares `deps: readonly Path<S>[]` (empty for `constant`/`ignore`), enforced by the union's base type.

**F28 — MEDIUM — CAP-9's delivery path to `@nestjs/swagger` is unowned.**
`@nestjs/swagger` is listed as a peer, but the OpenAPI back-end lives in `core/schema` and AD-6 says `core` imports nothing. CAP-9's success is measured against "what hand-written property decorators would have produced" — i.e. the schema must reach the actual Swagger document. Who bridges `core`'s neutral `OpenApiSchema` into Swagger's registry, and whether the swagger peer is optional, is undecided. **Fix:** assign the bridge to the `nestjs` package, state that `core/schema` emits a neutral shape only (mirroring AD-10's `FieldSelection` treatment — a good existing pattern to reuse), and mark `@nestjs/swagger` an optional peer.

**F29 — MEDIUM — AD-11 pins stack versions inside an invariant.**
"Emit with TypeScript 6.x" is a Stack fact with a shelf life; the durable rule is the no-plugin guarantee plus "the published `.d.ts` must type-check under every supported consumer major". Version-pinned invariants go stale and then get ignored wholesale, taking the no-plugin guarantee with them. **Fix:** split AD-11 — keep the no-plugin guarantee and the dual-major type-check obligation as the invariant; move the specific majors to the Stack table.

### LOW

**F30 — LOW — AD-3's identifier alphabet (`s`, `d`, `v0…vN`) is seed detail inside an invariant.** The invariant is "identifiers in generated source are emitter-controlled and never user-derived"; the specific letters are owned by the emitter once it exists. Harmless but it invites a spurious "spine violation" when someone renames `v0` to `t0`. **Fix:** state the property, put the alphabet in a code comment.

**F31 — LOW — "Every AD that is mechanically checkable gets a test" does not say which ADs those are.** Two implementers will draw the line differently. **Fix:** mark each AD with its check mechanism (`tsc`, lint rule, unit test, CI job, or "review only").

**F32 — LOW — `runtime/` has no slot in the compiler paradigm.** The Design Paradigm table maps front-end / lowering / IR / back-ends; `core/runtime` (identity map, ancestor chain, memo) is none of these, and `emit/` necessarily depends on it — an edge the "back-ends depend only on `plan/`" claim does not cover. **Fix:** add a "runtime support library" row to the paradigm table and carve it out explicitly in AD-1.

**F33 — LOW — AD-5's `Binds` is too narrow.** It binds CAP-3 and CAP-4, but errors are thrown on the CAP-5 path (projection without context), the CAP-6 path (underivable nested pair), and the CAP-7 path (depth ceiling, non-optional back-edge). **Fix:** `Binds: all`.

**F34 — LOW — `PlanReport` is CAP-3 output, not observability, and is undecided.** The "Observability envelope" deferral is otherwise correct for a library, but `validateAll(): PlanReport` is the CI-facing half of CAP-3 and its shape (machine-readable? exit code mapping? see F12) is neither decided nor deferred. **Fix:** fix `PlanReport`'s contract alongside the CLI decision.

## Internal consistency summary

Contradictions found between ADs, or between an AD and the rest of the document:

1. **AD-1 vs CAP-9/CAP-8** — back-ends banned from descriptor types but require descriptor-derived data (F1).
2. **AD-4 vs CAP-4** — `WeakMap`-permitting key rule vs a requirement to enumerate registrations (F4).
3. **AD-7 vs the api-surface's request-scoped ALS context** — two things named "context" with different lifetimes (F5).
4. **AD-10 vs the SPEC's projection constraint** — "unions their declared deps" reads as the union-across-contexts behaviour the spec forbids (F6).
5. **AD-2 vs Deferred #1** — AD-2 asserts a release-versioning policy while the Deferred section says versioning can wait (F13).
6. **AD-11 vs Deferred #1** — AD-11's only enforcement mechanism lives in a pipeline the Deferred section postpones (F11).
7. **AD-5 vs AD-1** — error taxonomy placed in a back-end directory that front-ends must import (F16).
8. **Design Paradigm vs Structural Seed** — five back-ends vs four, and the plan validator placed in the lowering stage (F15).
9. **`Binds:` fields vs the Capability→Architecture Map** — AD-3 and AD-6 bind capabilities the map never cites them for (F17).

## What the spine does well (stated only to avoid re-litigating it)
